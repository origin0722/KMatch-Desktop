# API 连通性扫描与性能优化备忘（2026-08-20）

> 环境：嵌入式后端（无 Docker / 无 LLM key）sidecar；扫描工具 `build/api_sweep.py`（本机 8000）。
> 版本：源码 main @ 本轮提交（含 deadlock 修复）；未升版本、未发版。

| 端点 | 方法 | 依赖 | 实测 | 结论 |

**扫描暴露的 1 个真缺陷（已修复+回归）**
- `EmbeddedGraphStore.update_node_status`：外层持 `_lock_for(path)`，内部 `_read_status()` 又对**同一把非可重入锁**嵌套获取 → 状态文件已存在时（第二次写）**自锁死锁** → PUT /status 永不返回。修复：`_read_status` 改为不加锁（锁由 `update_node_status` 唯一持有）；新增回归 `test_status_second_write_no_deadlock`。其余 FAIL 均为扫描脚本方法/路径写错（非应用问题）。

## 二、性能实测（嵌入式本地检索已是毫秒级）

- 图/题库读端点：2–36ms（含 HTTP 开销；首个请求含惰性载入 ~36ms，后续 3–18ms）
- BFS 路径组装 / 混合检索：15–17ms
- 判分/反馈/报告的"慢"= **LLM 调用**（ping 实测 3.1s 为网络+模型往返现实；判分 1 次 LLM + 内容生成并发）
- runs 列表 575ms（文件 IO，量小可接受）

## 三、优化清单（不改功能，按价值排序）

1. **✅ 已落地（本轮+前几轮）**：
   - 判分专属 45s/0 重试快失败；submit/feedback **async + 90s/120s 硬上限**（消除线程池排队假死）
   - 判分/反馈 每步耗时日志 + LLM 端点/模型留痕；错误真实原因上浮（不再 HTTP 0/未知错误）
   - 状态死锁修复；嵌入式递归题库；向量本地缓存 + 离线种子导出脚本
2. **候选（低风险 / 低收益，建议按需）**：
   - `kb_store` qid/节点索引缓存：KB CRUD 频次低，收益≈0，仅当题库文件量级暴涨时再做
   - 题库懒加载 per-node：当前 2–36ms 已达标，无必要
   - **SSE 进度流式化 submit/feedback**（最有体感收益）：把"静默等待"变成实时阶段进度；不改返回结果，仅改传输与 UI 呈现 — 列为下一轮候选
   - 判分走"快模型"开关（对齐反馈快模型模式）：牺牲微量精度换判分 1s 内返回 — 需评审

## 四、结论

- 全部 `kg/文件/JSON` 端点连通且毫秒级；LLM 类端点依赖 key（缺 key 快速失败并给出真实原因）。
- "题库/分析慢"的主因是 LLM 调用与网络，不是本地检索；已通过 async+超时上限+快失败把最坏等待从"静默 5 分钟"收敛到"≤90s 必有结果"。
- 状态条「纯图模式=黄色」为设计语义（琥珀=降级可用，非故障）。
