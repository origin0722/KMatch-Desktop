## C1 — 拆分 chat.js god store

- **Files** — `frontend/src/stores/chat.js`（1128 行）→ 拆出多模块；`aiSettings.js` 吸收配置。
- **Problem** — chat.js 混 6 职责：消息/chunk/version 模型、SSE 传输（双 transport）、工具定义+执行、provider/apiKey/model 管理、系统提示词构建、write_file 审批门。任何单点改动都要在 1100+ 行里定位；测试只能整体跑。AI 导航困难。
- **Solution** — 按 seam 拆分（顺序：先低风险后高风险）：
  1. **provider/model 配置 → aiSettings**：把 `provider/apiKey/customBaseUrl/model/models/fetchModels` 从 chat.js 移入 `aiSettings.js`，统一为一套 JSON blob 持久化（消灭散装 localStorage 键）。chat 只读 aiSettings。
  2. **tool registry 单一源**：新建 `frontend/src/ide/tools/registry.js`，`TOOLS` 定义 + `DEFAULT_TOOL_PERMISSIONS` + `toolCallExample` + `buildToolBlock` 统一来源；aiSettings 只存用户覆盖。消灭两处硬编码同名 6 工具。
  3. **SSE 传输 composable**：抽 `useChatStream`（`_streamResponse` + `_applySseBlock` + IPC/fetch 双 transport），chat store 调用它。
  4. **工具循环提取**：`sendMessage`/`regenMessage` 共享的 ~80% 逻辑（history 构建 → stream → split → execute → summarize）抽成 `_runToolLoop`，`toolResultSummary` 单一源。
  5. **消息模型 helpers**：`activeChunksOf/contentTextOf/thinkTextOf/splitToolCallChunks/appendTextChunk` 已是纯函数，抽 `frontend/src/ide/chat/model.js`。
- **Benefits** — leverage：chat store 接口收窄到"会话状态"，调用方不再面对 6 职责；locality：provider 配置变更集中在 aiSettings，工具增删集中在 registry。测试面收窄——model helpers / stream / tool loop 可独立测。deletion test：拆出后每块都集中了原本散在 chat.js 的复杂性（非 pass-through）。
- **Before/After**
  - Before：`chat.js` 1128 行 ← workspace, projectGraph, aiSettings, assessment；含配置+SSE+工具+模型+提示词+审批。
  - After：`chat.js`（会话状态 + 消息分支）+ `aiSettings.js`（全部 AI 配置）+ `tools/registry.js`（工具单一源）+ `chat/model.js`（纯 helper）+ `useChatStream`（传输）。
- **强度** — Strong（最高优先）。

## C2 — workspace → projectGraph 解耦

- **Files** — `frontend/src/stores/workspace.js:76`、`projectGraph.js`。
- **Problem** — workspace 文件监听回调里硬调 `useProjectGraphStore().markStale(path)`。workspace"知道" projectGraph 存在且关心文件变化，是硬编码观察者。动态 import + try/catch 已暴露耦合应力。
- **Solution** — 反转依赖：workspace 发"文件变化"事件（轻量 pub/sub 或 Pinia `$subscribe`），projectGraph 订阅并自行 `markStale`。workspace 不再 import projectGraph。
- **Benefits** — locality：projectGraph 的失效逻辑收回 projectGraph 自己；workspace 回归纯文件状态。leverage：未来别的 store 想监听文件变化只需订阅，不污染 workspace。deletion test：删 projectGraph，workspace 仍完整工作（事件没人接就是 no-op）。
- **强度** — Worth exploring。

## C3 — profile / knowledgeGraph 类型契约

- **Files** — `chat.js:177-222`（`buildSystemPrompt`）、`assessment.js`、新建 `frontend/src/ide/chat/types.js`（JSDoc）。
- **Problem** — chat 的 `buildSystemPrompt` 硬编码 assessment 内部字段名（`profile.theory_level`、`weak_topics[].name/.node_id`、`knowledgeGraph.learning_path.length`）。assessment 改 schema，chat 的提示词静默崩，无类型契约。
- **Solution** — 抽 JSDoc 类型定义 `Profile`/`KnowledgeGraph`/`LearningReport`，assessment 导出类型注释，chat 经类型化 helper 读取（如 `profileWeakTopics(profile)`）。不改运行时行为，只加契约。
- **Benefits** — leverage：chat 不再知道 assessment 内部形状，只知接口；locality：schema 变更在 assessment + 类型文件同步。AI 导航：类型即文档。
- **强度** — Worth exploring。

## C4 — session.js 去留

- **Files** — `frontend/src/stores/session.js`（41 行）。
- **Problem** — 近 pass-through：只拥 `splitView`，`activeStage` 是 assessment 的纯派生。单文件 store 价值边际。
- **Solution** — **保留**（建议）。理由：`splitView` 是 IDE 布局状态，与 assessment（学情领域）不是同一关注点；并入 assessment 会让领域 store 混入布局职责，反而耦合。session 作为"学习会话布局"独立 store 合理。仅补文件注释说明边界。
- **强度** — Speculative（建议不动，仅注释）。
