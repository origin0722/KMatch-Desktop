### 2.2 [config.py](backend/app/config.py) — 整体评价: 良好

**发现 1: EMBEDDING 默认值存在陷阱 🟡中**

```python
# 第 33 行
EMBEDDING_BASE_URL: str = os.getenv("EMBEDDING_BASE_URL", "") or os.getenv("LLM_BASE_URL", "https://api.deepseek.com/v1")
```

**问题**: 当用户不设置 `EMBEDDING_BASE_URL` 且设置了 `LLM_BASE_URL` 时，embedding URL fallback 到 DeepSeek 的 endpoint。但 DeepSeek **不提供 embedding API**，`text-embedding-v2`（千问模型）调 DeepSeek URL 必然报错。`create_embedding_client()` 中的测试调用会返回 None，语义检索静默降级为纯图模式——用户无感知。

**建议**: 默认 `EMBEDDING_BASE_URL` 改为千问 DashScope URL（与 .env.example 一致），或至少文档标注此陷阱。`docker-compose.yml` 已正确配千问 URL，本地开发需注意。

### 2.3 [engine.py](backend/app/graph/engine.py) — 整体评价: 良好

**发现 2: `get_node()` 未剥离 `embedding` 字段 🟡中**

```python
# 第 148-154 行 — get_node() 直接 dict(record["n"])，不调用 _node_from_record
def get_node(self, node_id: str) -> Optional[dict]:
    ...
    return dict(record["n"]) if record else None
```

**对比**: `get_by_category()`、`get_by_difficulty()`、`get_by_tags()`、`get_prerequisites()`、`get_dependents()` 全部通过 `_node_from_record()` 剥离 `embedding` 字段。

**影响**: `get_node()` 返回包含完整 embedding 向量（1536维 float 数组）的 dict，被 `semantic_search()` 和 `hybrid_retrieve()` 中的 weak_summaries 查询调用（第 310 行）。这会导致：
1. 网络传输浪费（每次 ~6KB 无用数据）
2. 与其他 getter 方法的行为不一致
3. `_node_from_record()` 的 docstring 说 "排除 embedding 字段" 但此处不生效

**发现 3: `assemble_learning_path` 中 f-string 注入 `max_depth` 🟢低**

```python
# 第 383-391 行
MATCH path = (start:KnowledgeNode)<-[:REQUIRES*1..4]-(n:KnowledgeNode)
```

`*1..4` 硬编码 OK（与 BUG-007 已记录一致），但建议统一为 `{max_depth}` 参数化，与其他方法风格一致。

### 3.2 [orchestrator.py](backend/app/agents/orchestrator.py) — 整体评价: 优秀

**发现 4: `datetime.utcnow()` 已弃用 🟢低**

```python
# 第 47 行
msg = f"[{datetime.utcnow().isoformat()}] ✅ 流程结束 (审核通过)"
```

Python 3.12+ 中 `datetime.utcnow()` 被标记为 deprecated。应使用 `datetime.now(datetime.UTC)` 替代。同样的问题也出现在 `diagnostics.py` 第 224 行和 `reviewer.py` 第 153/165/210 行——共 5 处。

**影响**: 当前仍能正常运行，但未来 Python 版本可能移除。建议第 3-4 周统一替换。

### 3.3 [diagnostics.py](backend/app/agents/diagnostics.py) — 整体评价: 良好

**发现 5: `_parse_json` 函数与 reviewer.py 完全重复 🔴重复代码**

两个文件中存在完全相同的 `_parse_json` 函数（各约 28 行）。包括：
- Markdown 代码块剥离 (` ``` `)
- `json.JSONDecoder().raw_decode` 容错解析
- 兜底 `json.loads`

**建议**: 提取到 `app/utils/json_utils.py` 统一维护。修改一处即可生效两处。

**发现 6: `_grade` 函数 `total_count` 与实际评分数量不一致 🟡中**

```python
# 第 181 行
"total_count": len(questions),  # 始终=出题量
```

但 `grades` 数组可能比 `questions` 短（LLM 返回不足），导致正确率计算偏差。例如：10 道题，LLM 只评了 8 道，其中 6 道正确 → `correct_count=6`, `total_count=10` → 正确率 60%（实际应为 6/8=75%）。

**建议**: 改用 `len(grades)` 或实际评分的题目数量。

## 四、脚本审查

### 4.1 [validate_data.py](backend/scripts/validate_data.py) — 整体评价: 良好

**发现 7: `key_points` 最少数量校验与 Schema 不一致 🔴数据质量**

```python
# validate_data.py 第 94 行
if not isinstance(key_points, list) or len(key_points) < 2:
    errors.append("key_points 至少需要 2 条")
```

```json
// schema.json 第 43 行
"key_points": { "minItems": 3 }
```

**validator 要求 ≥2 条，Schema 要求 ≥3 条**。这意味着有 2 条 key_points 的节点会通过校验但违反 Schema。当前 92 个节点是否全部满足 3 条以上需要验证。

### 4.2 [import_knowledge_base.py](backend/scripts/import_knowledge_base.py) — 整体评价: 良好

**发现 8: `practice_questions` 被序列化为 JSON 字符串存入 Neo4j 🟡中**

```python
# 第 149-152 行
"practice_questions": json.dumps(
    node.get("practice_questions", []),
    ensure_ascii=False,
),
```

**影响**: Neo4j 中 `practice_questions` 是字符串而非数组，Cypher 无法索引嵌套字段（如按 `type` 筛选题目）。后续 Cypher 查询如 `WHERE n.practice_questions[0].type = 'choice'` 将报错。

**评估**: 当前代码未对 practice_questions 做 Cypher 层查询（题目生成在 LLM 侧完成），暂无实际影响。但如果第 4 周 content_generator 需要按题型从图谱取题，会踩坑。建议改为 `neo4j` list 类型存储或提前迁移。
