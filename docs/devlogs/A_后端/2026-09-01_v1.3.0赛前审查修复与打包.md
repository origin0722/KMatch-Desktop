## 一、AI 助手回答截断（根因：模型输出上限 + 思考挤占预算，全链路无截断信号）

排查结论（三处叠加）：

1. 后端 SSE 流从不读 `finish_reason`——模型因 max_tokens 停笔时前端收到的是正常 `[DONE]`，用户把「戛然而止」当「答完了」；
2. DeepSeek-V4 默认档强制 `thinking:enabled`，思考内容计入输出预算，挤占正文 token；
3. Agent 层 `ChatOpenAI` 不设 `max_tokens`，长讲义/实操被厂商默认 8K 拦腰截断（`parse_llm_json` 吃残缺 JSON 判失败）。

修复（截断治理）：

- `backend/app/api/chat.py`：`_stream_openai` 读 `finish_reason=='length'` → 发 `{"truncated": true}` 帧；`_build_request_extras` DeepSeek 思考仅 `high/max` 显式开启，`default` 不传（跟随模型默认）。
- `frontend/src/stores/chat.js`：`_applySseBlock` 消费 `truncated` 帧，追加「已达到输出上限」提示（WeakSet 去重只提示一次）；`MAX_TOOL_ROUNDS_DEFAULT` 6→8。
- `backend/app/agents/llm.py` + `config.py`：`get_chat_model` 支持 `max_tokens`，默认 `LLM_MAX_TOKENS=16384`（.env.example 同步）。
- `frontend/src/ide/AssistantPanel.vue`：代码块 `max-height 200→480px` + `pre.expanded` 解除限高；`MarkdownViewer.vue` 代码块头加「展开/收起」按钮（流式重绑）。
- 流式尾部防御：`useChatStream.js`（fetch 回退路）与 `electron/main/ipc/http-proxy.js` done 后 flush 残留半帧。

## 六、追查：「刚生成的 key 却 401」——根因是 Windows 系统代理

用户反馈新生成的 key 不可能失效。复测取证：

- 用应用存储的 key 直连 `api.deepseek.com/v1/models` → **200**，模型列表含 `deepseek-v4-flash/v4-pro`（key 与模型名均有效）；
- 走系统代理 127.0.0.1:7897 → 200；后端 `/api/agents/ping` 用同 key → **ok:true**（链路此刻全通）。

结论：**key 有效，401 不是 DeepSeek 判的**。真正的坑：Windows 系统代理开启（注册表 ProxyEnable=1，ProxyServer=127.0.0.1:7897，典型 Clash/V2Ray）。应用内未配置代理时 `proxyEnv()` 返回 `{}`，Python httpx/openai SDK 在 Windows 上自动读注册表系统代理 → 后端所有 LLM/Embedding/Tavily 出站绕代理软件；代理软件未启动 → 「网络错误」，代理软件异常状态改写响应 → 「401」。用户按「key 无效」排查永远无解。

修复（已验证）：`electron/main/ipc/proxy.js` `proxyEnv()` 在未配置应用内代理时注入 `NO_PROXY='*'`（实测 httpx 尊重该通配并绕过系统代理直连）；应用内显式配置代理时维持原行为（代理 + 回环 NO_PROXY）。`backend/app/agents/llm.py` 的 401 提示同步补充「检查系统代理/VPN」引导。重打包 sidecar + 安装包。
