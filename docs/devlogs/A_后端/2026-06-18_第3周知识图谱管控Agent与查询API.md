## 三、关键设计决策

### 1. graph_controller 只在画像审核通过后运行（非破坏性）

工作流从 `diagnostics → reviewer → (loop) → finish` 扩展为：

```
diagnostics → reviewer ─┬─ 通过 → graph_controller → finish
                        ├─ 未通过 & retry<max → diagnostics (打回)
                        └─ 未通过 & retry≥max → finish (降级，不组装图谱)
```

**为什么不引入图谱审核循环**：reviewer 当前审核对象是画像（BUG-016 记录：第4周内容生成就位后切换审核对象为生成内容）。第3周图谱组装是确定性 engine 逻辑，无需独立审核循环；强行加图谱审核会与 BUG-016 的审核对象迁移耦合，增加风险。图谱组装的轻量自校验（路径非空、异常不中断）已在节点内完成。

### 2. 纯函数提取保证可测

graph_controller 节点闭包注入 `kg`（不可纯单测），但把可测逻辑抽为纯函数：
- `_derive_max_nodes(time_per_week)` — 节点数上限（time_per_week×2，[4,20]）
- `_compute_estimated_hours(path)` — Σ estimated_minutes/60
- `_derive_status_updates(profile, path)` — known→mastered / weak→difficult / 路径首节点→in_progress

状态优先级：weak(difficult) > known(mastered) > 首节点(in_progress)。弱项若恰为路径首节点，保持 difficult 不被 in_progress 覆盖。

### 3. 节点状态写回用 try/except 逐条保护

`update_node_status` 逐条写回 Neo4j，单条失败不影响其他节点与工作流（仅 logger.warning）。与 diagnostics/reviewer 的"异常不中断工作流"原则一致。

### 4. 图谱查询 API 直接复用 engine，不重复实现

`api/graph.py` 是薄封装层：参数校验（Pydantic + Query 约束）+ 404/400/503 语义 + 转发 engine 方法。engine 已在第1周充分测试，API 层不重复业务逻辑。语义检索 (`/search`) 在 embedding_client 未配置时返回 503 引导改用图遍历类查询。

## 四、API 清单（/api/graph 前缀）

| 方法 | 路径 | 说明 |
|:---|:---|:---|
| GET | /node/{node_id} | 按节点 ID 查询（404 不存在） |
| GET | /category/{category} | 按分类查询 |
| GET | /difficulty?min_d=&max_d= | 按难度区间 |
| GET | /tags?tags=a,b | 按标签（任一命中） |
| GET | /prerequisites/{node_id} | 前置依赖 |
| GET | /dependents/{node_id} | 后继依赖 |
| GET | /search?q=&top_k=&difficulty_max= | 语义向量检索（embedding 未配置→503） |
| POST | /hybrid | 图遍历+向量混合检索 |
| POST | /path | 组装个性化学习路径 |
| PUT | /status/{node_id} | 更新节点掌握状态 |
