## 三、关于 question JSON 文件增多的架构判断

**结论：当前架构已将"文件数增长"与"运行时性能"解耦，无需额外存储服务。**

两套存储职责分离：
- **磁盘 JSON**（`data/knowledge_base/questions/*.json`）：题目源文件，仅供 import 脚本读，受 git 版本控制（可审、无幻觉证据）
- **Neo4j `:Question` 节点**：运行时题目，带 `source_node_id/type/difficulty` 三索引，diagnostics 出题走 Cypher 查询

运行时不碰 JSON 文件——出题响应亚毫秒级索引扫描，与文件数无关。文件从 92 涨到 5000，出题时间不变。git 管理几 MB 级 JSON 无压力。

未来若题目多到手改累，需要的是**题目管理 CRUD 界面**（编辑体验问题），而非引入对象存储服务（那是过度设计）。扩域时只需 `generate_practice_questions.py` 对新领域跑一遍 → import → 索引自动覆盖。

## 四、场景二（用户上传项目→Agent 构建理解图谱+知识点图谱）可行性分析

**结论：当前代码框架完全支持，且 W6 已实现核心链路。无需新增 Agent。**

场景二在 W6 已交付全链路（`/api/project` 路由）：
```
用户上传项目 → code_parser(AST+Jedi 解析) → engine.write_project_graph(落 Neo4j 第2/3层)
  → /api/project/graph (G6 结构返回) → code_reviewer (AST安全+LLM领域规范审查)
  → code_tester (图谱驱动 Pytest 生成+分层沙箱+覆盖率+反向标注风险节点)
```

即用户上传项目文件后，Agent 已能：
1. **构建项目理解图谱**：code_parser 提取函数/类/方法/参数/调用/继承，engine.write_project_graph 落 Neo4j 四层图谱的项目框架层(2)/代码实体层(3)，`:ProjectEntity` 命名空间隔离
2. **构建知识点图谱**：engine 的 `link_entity_to_knowledge` 将代码实体链接到领域元知识节点（第1层），annotate_risk 反向标注掌握度风险节点

**与用户设想的差距**（可选增强，非必需）：
- 当前 code_parser 输入是**本地路径**（`data/example_projects/`），用户"上传文件"需 B 端做文件上传组件 + A 端加 `/api/project/upload` 接收文件落临时目录再解析——这是**接入层**工作，不涉及 Agent 框架改动
- "知识点图谱"当前是代码实体→元知识节点的**链接关系**，若要更深度（如自动识别项目用了哪些知识点、缺哪些），可在 code_reviewer/code_tester 基础上扩展，但 W6 链路已覆盖核心

**所以：场景二的 Agent 构建图谱能力，当前框架已实现，是 W6 的成果。** 用户设想的功能本质是场景二已交付内容的另一种表述。待 B 端 ProjectUpload 页面接入 `/api/project` 路由即可演示。
