## 三、关键设计决策

### 3.1 `per_node` 适配选择"全量重建映射"而非"流式累加"

旧代码用 `nodeCounters` 在遍历 `questions` 时按顺序消费每个 node 的判分数组。一旦上游答案与题目顺序错位（如 LLM 返回数量不对齐 → A-6 已加 warning），整张报告全部错位。

新方案直接构造 `question_index → {node_id, correct}` 反向映射，O(N) 一次扫描，完全无序消费，**任何顺序错位都退化为单题判分缺失（显示"未判分"）而不是整体错位**。代价：多扫一次 per_node（其总长度 ≤ 题目数）。

### 3.2 ECharts 按需引入只引 5 个模块

仅雷达图用到：`RadarChart`（图表本体）+ `CanvasRenderer`（渲染器）+ `GridComponent` `LegendComponent`（坐标系/图例）+ `core`（注册中心）。
**不引** `TitleComponent` / `TooltipComponent`（雷达图默认 tooltip 已够用，title 由外层组件用 Element Plus 渲染）。
若后续 Dashboard 引入折线图/饼图，需要在该组件文件**自己** `echarts.use([...])`，不复用 ProfileRadar 的注册（避免组件耦合）。

### 3.3 AbortController 放在 store 而非组件

放 store 的好处：`reset()`、路由切走（如未来加 `onBeforeRouteLeave` hook）、新一次提交都可统一调 `abort()`，单一入口。
放组件会导致每次组件卸载/重挂载丢失 controller 引用，跨组件场景（如 AgentView 也想取消）无法复用。

### 3.4 vitest 用 happy-dom 而非 jsdom 作为默认 environment

测试启动时间：happy-dom < 0.1s，jsdom ~0.5s。Element Plus 组件在 happy-dom 下也能挂载（仅在动画/Transition 测试中可能需切 jsdom）。当前 3 个测试均使用浅渲染 + 纯 store 调用，happy-dom 完全够用。`jsdom` 作为 devDependency 保留，给后续做端到端组件测试时备用。

## 四、踩坑

### Pitfall-1: `el-input-number` 默认 `step=1` 但需显式 `:min` `:max` 才会拦截非法值

最初没加 `:min :max`，用户可以输入 0 或 999。加上后边界生效。
**记录**：el-input-number 不通过 v-model 类型约束（仍是 number），需配合 `:min :max` 才安全。

### Pitfall-2: vitest 4.x 默认不再隐式注入 `expect`

vitest 3.x 起 `expect` 在文件作用域全局可用，4.x 严格模式默认开启 `globals: false`。解决：在 `vitest.config.js` 显式 `globals: true`，或测试文件 `import { describe, it, expect } from 'vitest'`。
本次选 `globals: true` 路线（与 jest 习惯一致，组员上手成本低）。

### Pitfall-3: ProfileRadar 改成按需引入后，本地 `npm run dev` HMR 偶发 `echarts is not a constructor`

原因：旧版本 Vite 缓存的 `optimizeDeps` 还包含全量 echarts。
**解决**：`rm -rf node_modules/.vite && npm run dev`。
**预防**：`vite.config.js` 后续可加 `optimizeDeps.exclude: ['echarts']` 让 Vite 不预构建。
