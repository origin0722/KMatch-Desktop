# KMatch·知链：画像、Agent 协同、历史与体验升级总方案

> 日期：2026-09-02  
> 面向：赛题 XH-202630、KMatch-Desktop v1.3.1 后续迭代  
> 目标：在不破坏现有闭环和比赛证据的前提下，解决画像泛化、Agent 状态歧义、历史割裂、图谱功能含混、界面“AI 模板感”、底层契约与运行时存储风险，并形成可演示、可验收、可追溯的专业学习平台。

## 0. 执行摘要

### 0.1 总体判断

当前产品已经具备赛题要求的核心闭环：学情诊断、图谱组装、内容生成、内容审核、质量裁判、反馈迭代、项目代码审查与测试。下一阶段不应继续横向堆叠大量入口，而应围绕四条主线深化：

1. **画像从“Python 问卷”升级为“跨领域、可进化、带证据的学习者模型”**。
2. **Agent 从“固定头像状态列表”升级为“按运行和阶段组织的可解释证据链”**。
3. **历史从多个页面各自缓存升级为“运行主线 + 产物快照”的统一档案**。
4. **体验从“功能齐全”升级为“信息克制、状态可信、动效稳定、可用于比赛演示”**。

### 0.2 对问题的直接结论

| 用户问题 | 当前判断 | 方案结论 | 优先级 |
|---|---|---|---:|
| 快问卷是否需要优化 | 需要；字段和题干仍偏 Python/编程，VARK 被表述得过于像固定人格标签 | 改为条件问卷；把“学习风格”改成“内容呈现偏好”，并结合真实行为动态校正 | P1 |
| 不学 Python 却询问 Python 经验 | 是明确的跨领域缺陷 | 按目标领域动态显示“当前领域经验”；仅 Python 方向显示 Python 经验 | P0/P1 |
| 原始画像是否有用 | 有用，但用途不是替代真实用户画像 | 保留为匿名测试夹具、M5 回归集、比赛演示样例；迁移到通用 schema，并补非 Python 样例 | P1 |
| 设置中是否单独增加画像页 | 应增加，但放在设置中心内部，不再增加一级主导航 | 将设置改为分类子页；“学习画像”成为独立设置页 | P1 |
| 内容审核 Agent 一直未完成 | 主要不是渲染偶发故障，而是流程契约与界面语义不一致 | 区分“诊断流程”和“资源生产/审核流程”；事件按 `stage_id` 聚合，不能只按 Agent 名称聚合 | P0/P1 |
| 图谱、资源是否需要历史 | 需要，尤其是比赛中的可追溯与个性化演进证据 | 统一为运行产物；支持只读回看、比较、单项删除和批量管理 | P1 |
| 是否区分初学/项目二开 | 必须区分 | 使用赛题原词“无项目技能学习 / 有项目二次开发”，提供筛选、分组和不同标题规则 | P0 |
| 标题是否用项目名/垂直领域 | 应使用 | 场景一显示垂直领域或学习目标；场景二显示项目名 + 项目质量流水线 | P0 |
| Emoji 是否太多 | 是，产品框架内的硬编码 Emoji 会削弱专业感 | 产品状态、导航和指标统一使用单色图标/状态点；保留用户内容中的自然 Emoji | P0/P1 |
| 数据面板能否更高级 | 可以，但不能靠堆图表 | 加入跨运行趋势、阈值、证据来源、质量裁判口径和下钻链路 | P2 |
| API/框架是否要优化 | 需要；存在契约、存储路径、依赖安全与大模块问题 | 先做安全和数据路径，再做事件/API 深化，最后分离升级 Electron/Vite | P0-P2 |
| 协同流水线是什么 | 当前名称大于实际范围；前端事实上只检查当前活动文件 | 短期更名为“当前文件质量检查”；完整接线后再称“项目质量流水线” | P0/P1 |
| 如何透明化 Agent 思考 | 展示内部原始思维链并不合适，也不利于可信度 | 展示结构化过程：输入摘要、引用证据、规则阈值、阶段结论、复审意见、耗时与重试 | P1 |
| 还应增加什么 | 应优先增加能直接抬高赛题评分的证据功能 | 双画像对照、评审证据包、隐私中心、降级状态说明 | P1/P2 |

## 1. 设计边界与产品原则

### 1.1 不把偏好误写成能力

VARK 类问卷最多只能表达用户当下偏好的内容形式，不宜作为决定学习成败的固定类型。研究综述没有发现足够证据支持“按学习风格匹配教学方式就能提高成绩”；一项医学教育研究也未发现遵循 VARK 偏好与学习结果相关。因此产品应：

- 将“你是什么类型的学习者”改为“你当前更希望怎样呈现内容”；
- 允许多选和“不确定”，不强迫归为唯一类型；
- 只收集平台真正能兑现的偏好，例如图示、简明文字、完整推导、示例拆解、动手练习；
- 用后续行为证据校正偏好，例如资源展开、完成率、重试次数和反馈，而不是一次问卷永久定型；
- 允许不同领域拥有不同偏好，避免把 Python 学习偏好直接套到数据库、机器学习或其他新领域。

参考：[Pashler 等关于学习风格证据的综述](https://doi.org/10.1111/j.1539-6053.2009.01038.x)、[VARK 使用与学习结果研究](https://pubmed.ncbi.nlm.nih.gov/29533532/)。

### 1.2 透明化“过程与证据”，不展示内部原始思维链

可解释性应回答：

- 哪个 Agent 在什么阶段工作；
- 它接收了哪些经过脱敏的输入；
- 使用了哪些知识图谱节点、题目结果或代码证据；
- 按什么规则或阈值得出结论；
- 输出了什么结构化结果；
- 哪个 Reviewer/Judge 复核了结果；
- 是否发生降级、重试、申诉或定向再生；
- 最终产物与证据如何对应。

不应展示模型的隐藏思维链、原始系统提示词、密钥、完整用户代码或未经脱敏的交互日志。这样既能满足评委对“过程透明”的需求，也不会把模型自述误当作可靠证据。

### 1.3 历史的核心不是“多一个列表”，而是可追溯

运行、画像、图谱、资源和报告不应是五套互不相识的历史。统一关系为：

```text
一次运行 Run
  ├─ 输入快照：学习目标 / 项目范围 / 问卷答案
  ├─ 过程事件：Agent 阶段、决策、证据、重试
  ├─ 画像产物：画像版本与 diff
  ├─ 图谱产物：知识图谱或项目图谱快照
  ├─ 资源产物：讲义、实操、测试、外部链接
  └─ 评估产物：审核、Judge、M5 指标与反馈
```

### 1.4 赛前控制变更面

比赛提交前只合入可回归、可快速演示、不会改变核心生成逻辑的修复。Electron、Vite、事件协议和画像 schema 的大迁移应分支完成，不与赛前 UI 修复捆绑。

### 1.5 当前产品范围：学习引擎多领域，代码图谱仅 Python

KMatch·知链不应被定义为“只能学习 Python”。学习引擎当前有六个内置领域：Python 编程、数据分析与可视化、数据库与缓存、工程化实践、Web 后端开发、机器学习；目标不命中时，还可以经检索、LLM 建域和校验形成一个动态迷你知识域。动态领域可以进入测评、学习路径、内容生成、审核和知识图谱，但其知识事实主要来自生成和检索，不应与人工策展的内置领域使用同一 M5 质量承诺。

但项目图谱是另一条能力线，当前基于 Python `ast` 与 Jedi：

| 能力 | 当前范围 | 对外正确表述 |
|---|---|---|
| 学情诊断、路径、资源、知识图谱 | 六个内置学习领域 + 动态迷你领域 | 多领域个性化学习引擎 |
| 项目代码图谱 | 仅 `.py` 文件 | Python 项目代码图谱 |
| 代码审查、AST 安全检查、Pytest 沙箱 | 仅 Python | Python 代码质量协同 |
| 非 Python 文件 | 可在文件树预览、在项目页统计 | 当前不解析实体/关系，也不执行语言级审查与测试 |

界面、README 和答辩必须如实使用上述分层表述。不要把“可以输入 Java 学习目标”误说成“已具备 Java 项目代码图谱”；也不要因为项目图谱暂时只支持 Python，就把整个学习平台缩窄成 Python 学习工具。

## 2. 学习问卷与画像 v4

### 2.1 当前问题

现有 `StageGoal.vue` 同时承载目标选择、VARK 快问卷和背景信息，存在以下问题：

- 问卷中的学习场景、专业经验与 Python 经验过度面向编程；
- 目标方向已经能动态建域，但画像字段仍是固定 Python schema；
- 每周可用时间上限为 168 小时，不符合一般学习规划语境；
- 年龄段默认进入问卷，但当前个性化策略对它的使用价值较低；
- “学习风格”以单一最高票类型落库，缺少并列偏好、置信度和证据来源；
- 未填写时默认 `read_write`，界面很容易把“系统默认”误解为用户真实偏好；
- 真实用户画像、历史画像和比赛测试画像的用途边界没有在 UI 中讲清楚。
- AI 助手画像投影读取 `practice_level`，而运行时画像字段为 `practical_level`，导致实操等级没有进入助手上下文；
- `time_per_week` 在不同层出现 20、60、168 等不同上限，说明约束尚未形成单一真相源；
- 部分背景字段已经落库但没有明确生成策略消费，形成“采集了但没有产生个性化价值”的浅接口。

### 2.1.1 当前快问卷是否真的帮助学习

结论是：**有一部分直接帮助，但目前不值得把所有字段都继续保留。** 采集字段应满足“至少有一个明确消费者、能说明会怎样改变学习结果”的标准。

| 当前字段 | 当前真实消费者 | 对学习的真实作用 | 审查结论 |
|---|---|---|---|
| 学习目标 `target_direction` | 选知识节点、出题、动态建域、生成内容 | 很强，决定学习对象 | 保留，设为必填 |
| 答题结果 / 理论水平 | 路径、资源难度、审核 | 很强，属于高质量行为证据 | 保留，优先于自填经历 |
| 学历、专业 | 内容生成提示 | 有限但真实；改变术语密度和类比方式 | 可选保留，并说明用途 |
| 内容呈现偏好 | 资源生成提示 | 目前只影响表达形式，尚未验证提升结果 | 可选、可跳过，后续用行为校正 |
| 每周可用时间 | 学习报告的节奏估算 | 有帮助，但当前未稳定改变资源结构 | 保留，统一约束；只用于路径节奏 |
| 学习节奏 | 主要落库 | 当前没有稳定消费者 | 暂停采集，或先实现其消费逻辑 |
| 编程/Python 经验 | 主要落库 | 当前基本不参与资源生成或判分 | 改为按领域经验；迁移前不应强制询问 |
| 年龄段 | 没有明确策略消费者 | 不能证明改善学习 | 默认不采集 |

因此，快问卷的正确定位不是“凭五六个自填问题准确判断用户”，而是：用最低成本提供题目和资源的初始上下文；随后让答题、项目测试、资源完成和反馈成为更高权重的证据。若一个字段在采集后不能改变题目、路径、资源或反馈策略，就不应出现在快问卷中。

### 2.2 问卷改为三层渐进式收集

#### 第一层：必须项，30 秒内完成

| 字段 | 形式 | 作用 |
|---|---|---|
| 学习场景 | 无项目技能学习 / 有项目二次开发 | 决定工作流 |
| 目标领域 | 预设 + 自定义 | 动态建域和标题 |
| 目标结果 | 能理解 / 能做题 / 能完成项目 / 能排障 | 决定资源和评估侧重 |
| 当前熟悉度 | 首次接触 / 了解概念 / 做过练习 / 有项目经验 | 决定诊断题难度 |
| 每周可用时间 | 1–40 小时，允许“不确定” | 决定路径节奏 |

#### 第二层：可选项，提升个性化

| 字段 | 条件显示 | 说明 |
|---|---|---|
| 当前领域经验时长 | 所有领域 | 用通用名称，不写死 Python |
| 编程经验 | 软件开发类领域 | 非编程领域不出现 |
| Python 经验 | 目标为 Python 或 Python 项目 | 仅在相关场景出现 |
| 项目经验 | 场景二 | 可从当前工作区推断，用户只需确认 |
| 学历背景、专业 | 用户愿意填写 | 赛题明确要求背景适配，保留但说明用途 |
| 单次学习时长 | 需要排学习节奏时 | 比只问每周总时间更可执行 |
| 计划完成日期 | 用户有明确截止日期时 | 生成倒排路径 |

年龄段默认折叠到“更多背景”，并明确其用途；若后续策略没有使用，应删除该字段，遵守最少必要原则。

#### 第三层：内容呈现偏好，不再称固定“学习风格”

采用多选和排序，而非 5 道题强行归类：

- 我更希望先看：结构图 / 简要结论 / 完整推导 / 真实示例；
- 我更容易开始：分步引导 / 挑战任务 / 可运行模板 / 错误案例；
- 遇到困难时希望：换一种解释 / 更多例子 / 回到前置知识 / 直接动手调试；
- 每次内容长度：短卡片 / 标准章节 / 深入长文；
- 允许“暂不设置，由系统根据使用情况学习”。

### 2.3 条件问卷规则

建议将规则从组件模板中抽出，形成可测试的 `questionnairePolicy`：

```text
target = Python       -> 显示 Python 经验、编程经验
target = JavaEE       -> 显示 Java/JavaEE 经验、编程经验
target = 数据库        -> 显示数据库经验；编程经验为可选
target = 机器学习      -> 显示数学基础、Python/编程经验（可按路径需要）
target = 自定义非编程域 -> 只显示当前领域熟悉度/经验，不显示语言经验
scene = 项目二开       -> 优先从项目语言、框架和规模推断，用户确认或修正
```

规则输入应是领域能力标签，而不是硬编码目标名称：

```json
{
  "domain_id": "JAVAEE",
  "capabilities": ["software_development", "jvm"],
  "experience_fields": ["programming", "java"]
}
```

动态建域结果若尚未返回，先展示通用字段，建域完成后只补问真正有价值的问题。

```json

  "global_profile": {

    "exportable": true

```

设计要点：

- 全局层只存跨领域稳定信息；
- 领域层保存经验、掌握度和目标，避免 Python 经验污染其他方向；
- 每项推断记录 `source`、`confidence` 和 `evidence_refs`；
- 保留 `schema_version`，为后续迁移提供契约；
- Agent 暂时通过 v3 兼容适配器读取当前领域切片，避免一次性改完所有提示词和测试。

### 2.5 原有 10 组画像的处理

这些画像继续保留，明确标记为 `fixture`，用于：

- 赛题要求的至少 3 类不同背景/能力画像验收；
- 幻觉率、适配率、覆盖率的固定回归；
- 现场演示的可复现样例；
- 不暴露真实个人信息的测试数据；
- 同一目标在不同画像下的个性化对照。

迁移任务：

1. 将现有 10 组 v3 数据批量迁移到 v4；
2. 增加至少 3 组非 Python 样例，例如 JavaEE、数据库、机器学习；
3. 每组增加 `fixture_id`、`persona_purpose`、预期难度和预期资源差异；
4. 质量脚本仍使用固定版本夹具，不能自动读取真实用户画像；
5. UI 中出现演示画像时明确显示“演示数据”。

### 2.6 设置中心的独立画像页

现有 `ProfileSettings.vue` 已有基础能力，但它只是长设置页中的一个锚点。建议将 `SettingsView.vue` 改成分类壳：

```text
设置中心
  ├─ AI 助手
  ├─ 学习引擎
  ├─ 学习画像        <- 独立子页
  ├─ 模型与服务商
  ├─ 网络与运行时
  ├─ 数据与隐私
  └─ 外观与交互
```

“学习画像”页结构：

1. **概览**：画像完整度、最近更新、当前活跃领域；
2. **全局偏好**：时间、内容形式、学习节奏；
3. **领域画像**：按领域切换，显示经验、理论/实践水平、强弱项；
4. **证据与来源**：自填、答题、项目分析、行为推断分别标识；
5. **版本历史**：每次运行的画像变化及原因；
6. **数据控制**：导出、重置某一领域、删除全部画像、隐私说明。

它仍属于设置中心，不新增一级侧栏入口，以免主导航继续膨胀。

## 3. Agent 状态、审核闭环与可解释协同

### 3.1 “内容审核一直未完成”的根因

当前交互测评实际只运行：

```text
学情检测 -> 图谱组装
```

内容生成与内容审核要到学习报告/资源生成请求才触发。但是 `StageAgent.vue` 固定展示五个 Agent，未触发阶段仍显示“待触发”；用户自然会把它理解为流程卡住。

更深一层的问题是：同一个 `reviewer` Agent 在完整流程中承担“画像审核”和“内容审核”两个阶段，而前端状态只按 `agent` 名称聚合。即使完整流程运行，两个阶段也可能相互覆盖，无法稳定表示“哪个审核已完成”。现有单元测试也明确把交互模式中的内容生成和 Reviewer 断言为 idle，说明这是当前契约行为，而不是简单 CSS 故障。

### 3.2 P0 语义修复

赛前先修用户理解，不伪造完成状态：

- 交互测评结束后，将当前流程命名为“诊断流程”；
- 只展示本次实际参与的 Agent；
- 对未触发阶段显示“将在生成学习资源时启动”，不用“待完成”；
- 增加主操作“生成并审核学习资源”；
- 若自动启动后台生成，则显示“已转入资源生产流程”；
- `reviewer` 显示为具体角色实例：“画像复核”和“内容审核”。

### 3.3 AgentEvent v2

长期修复必须把状态主键从 Agent 名称改成运行中的阶段实例：

```json
{
  "event_id": "evt_01",
  "run_id": "run_01",
  "seq": 17,
  "timestamp": "2026-09-02T10:00:00.000Z",
  "workflow_id": "scene1-loop",
  "stage_id": "review-content",
  "agent_id": "reviewer",
  "kind": "stage.completed",
  "status": "completed",
  "attempt": 1,
  "message": "内容审核完成",
  "input_summary": {"resource_count": 3},
  "output_summary": {"approved": 3, "flagged": 0},
  "decision": {"result": "pass", "threshold": 0.85},
  "evidence_refs": ["graph:PY-BAS-01", "artifact:resource-01"],
  "duration_ms": 1842,
  "model_provenance": {"role": "reviewer", "provider": "redacted"}
}
```

关键约束：

- `run_id + stage_id + attempt` 唯一标识阶段实例；
- `seq` 保证 SSE 重连和乱序事件可重放；
- 状态只允许 `queued/running/completed/degraded/failed/cancelled/skipped`；
- Agent 日志是展示材料，事件才是状态真相源；
- v1 Emoji 日志通过适配器读取，但不再生成新的推断型状态；
- 所有摘要默认脱敏，完整代码只保留在本地受控产物中。

### 3.4 Agent 协同界面

界面采用三层信息密度：

#### 第一层：流程总览

显示阶段 DAG、当前阶段、总耗时、是否降级、质量是否达标。评委可以在 10 秒内看懂闭环。

#### 第二层：阶段卡片

每个阶段展示：

- 角色与职责；
- 输入摘要；
- 使用的知识节点/代码位置；
- 阶段产物；
- 结论与阈值；
- 耗时、重试和降级；
- 跳转到对应图谱、资源或报告。

#### 第三层：证据抽屉

面向需要核验的用户和评委，展示：

- 结构化引用；
- 图谱节点版本；
- 题目或测试结果；
- Reviewer 与独立 Judge 是否一致；
- 申诉和复审记录；
- 定向再生前后差异。

不展示隐藏思维链；界面文案使用“决策依据”“检查项”“证据”“结论”，不使用“AI 内心思考”。

### 3.5 审核和准确性闭环

场景一建议明确显示：

```text
学情检测
  -> 画像复核
  -> 图谱组装
  -> 资源生成
  -> 内容审核
  -> 独立质量裁判
  -> 不达标：定向再生 -> 再审核
  -> 达标：交付与反馈
```

准确性证据至少包括：

- 每项资源覆盖的知识节点；
- 节点与内容的锚定覆盖率；
- Reviewer 四维结论；
- Judge 的幻觉、难度、覆盖判定；
- 同源审核与独立裁判的明确标识；
- 失败后的修正提示和再生次数；
- 最终 M5 三项指标与阈值。

## 4. 运行历史、图谱历史与资源历史

### 4.1 当前问题

- `RunsPanel.vue` 已尝试读取 `request` 中的场景和目标，但后端 `list_runs()` 没有返回 `request`，真实列表很难显示正确标题；测试使用了比真实 API 更丰富的 mock，未覆盖这项跨层契约；
- 图谱历史使用 localStorage，最多保留 12 条，并且已有 `remove(id)`，但页面没有提供单项删除；
- 项目图谱历史保存的是后端图谱指针，学习图谱历史保存本地快照，两者语义不同；
- 学习资源只在 Pinia 内存中，刷新后无法形成可靠历史；
- 运行记录没有统一关联画像 diff、图谱、资源、审核报告和项目流水线结果；
- 运行与画像档案当前使用 `DATA_DIR`，而安装包的可写用户数据主路径是 `LOCAL_DIR`，存在升级、安装目录权限和数据迁移风险。

### 4.2 统一运行摘要契约

`GET /api/runs` 不再依赖前端解析任意 `request`，直接返回可显示字段：

```json
{
  "run_id": "run_01",
  "display_title": "JavaEE 企业应用开发",
  "scene": "skill_learning",
  "scene_label": "无项目技能学习",
  "target_direction": "JavaEE 企业应用开发",
  "project_id": null,
  "project_name": null,
  "workflow_id": "scene1-loop",
  "status": "completed",
  "created_at": "2026-09-02T10:00:00Z",
  "updated_at": "2026-09-02T10:03:20Z",
  "artifact_counts": {"profile": 1, "graph": 1, "resource": 3, "report": 2},
  "summary": "完成诊断、资源生成和独立裁判"
}
```

标题规则：

- 场景一：`学习 · {垂直领域或具体目标}`；
- 场景二：`{项目名} · 项目质量流水线`；
- 只有诊断：`测评 · {垂直领域}`；
- 只有图谱解析：`{项目名} · 项目图谱`；
- 同名追加日期或简短序号，不使用完整 session UUID 作为主标题。

### 4.3 运行分类与查找

运行历史增加：

- 场景筛选：无项目技能学习 / 有项目二次开发；
- 目标领域筛选；
- 项目筛选；
- 状态筛选：进行中、已完成、降级、失败、已取消；
- 时间范围；
- 标题/领域/项目关键字搜索；
- 最近使用置顶；
- 分页或增量加载，不再静默只留固定条数。

文案统一使用赛题领域词汇，不使用“初次对话”等容易和聊天混淆的名称。

### 4.4 Artifact Store

运行元数据保持轻量，产物单独存放：

```text
LOCAL_DIR/
  profiles/
  runs/{run_id}/run.json
  artifacts/{run_id}/manifest.json
  artifacts/{run_id}/profile-diff.json
  artifacts/{run_id}/knowledge-graph.json
  artifacts/{run_id}/resources.json
  artifacts/{run_id}/review-report.json
  artifacts/{run_id}/project-pipeline.json
```

产物清单包含：

```json
{
  "artifact_id": "resource-set-01",
  "run_id": "run_01",
  "type": "learning_resources",
  "title": "JavaEE 事务管理学习资源",
  "created_at": "2026-09-02T10:02:00Z",
  "schema_version": "1.0",
  "path": "resources.json",
  "provenance_refs": ["stage:content", "stage:review-content"],
  "content_hash": "sha256:..."
}
```

### 4.5 删除语义

删除不能只放一个垃圾桶图标而不解释后果：

| 操作 | 删除内容 | 不删除内容 | 是否确认 |
|---|---|---|---|
| 从最近记录移除 | 列表索引/置顶关系 | 运行与产物本体 | 轻确认 |
| 删除单个资源历史 | 指定资源产物 | 同次运行、图谱、画像累计结果 | 确认 |
| 删除图谱快照 | 指定历史快照 | 当前知识库与画像 | 确认 |
| 删除一次运行及产物 | run、事件和所属产物 | 已合并进稳定画像的掌握度 | 强确认并提示 |
| 删除项目图谱缓存 | 项目解析缓存和指针 | 项目源代码 | 强确认 |
| 清空全部学习数据 | 画像、运行和产物 | 项目源文件、API 配置（除非勾选） | 二次确认 |

删除 API 必须使用明确的资源 ID，禁止由前端拼接任意路径。批量删除返回成功、失败和未找到项的明细。

### 4.6 历史页与各功能页的关系

- 运行历史是总入口；
- 知识图谱页显示最近图谱快照，可跳到所属运行；
- 学习资源页显示最近资源集，可跳到审核证据；
- 项目图谱页显示该项目的解析/流水线历史；
- 画像页显示跨运行聚合趋势和每次 diff；
- 同一产物只保存一次，各页面使用引用，避免多套存储相互漂移。

## 5. 知识图谱、项目图谱与协同流水线

### 5.1 当前“协同流水线”为什么难理解

前端按钮位于项目图谱页，但当前实现读取的是活动编辑器中的一个 `.py` 文件，并提交给项目审查与测试链。后端虽然能处理有限文件集合，当前前端请求仍是单文件文本。因此“项目协同流水线”这个名称让用户合理地期待全项目分析，实际范围却是当前文件。

当前真实行为可以准确描述为：

```text
读取当前 Python 文件
  -> 代码审查：规范、风险、知识点
  -> 代码测试：生成并在沙箱运行测试
  -> 汇总失败证据
  -> 生成修复建议
```

它是只读质量检查，不会自动修改代码。

此外，当前入口代码读取 `store.profile`，但该视图没有定义对应的 `store`。这是一个可直接导致点击流水线后出现 `ReferenceError` 的独立 P0 缺陷，应先修复，再讨论能力扩张。

### 5.2 两阶段处理

#### P0：诚实命名与说明

- 按钮更名为“检查当前文件”；
- 按钮旁提供一句说明：“由代码审查与代码测试 Agent 协同，生成只读修复建议，不会修改源文件”；
- 运行前显示文件名、语言、预计阶段；
- 非 Python 文件显示当前能力边界，不制造“已支持”错觉；
- 结果写入运行历史，避免关闭弹窗后丢失。

#### P1：真正的项目质量流水线

- 支持选择范围：当前文件、选中文件、变更文件、项目目录；
- 运行前预检文件数量、语言、忽略规则、沙箱能力；
- 大项目先做符号/依赖筛选，不无上限上传所有源码；
- 将审查结果锚定到项目图谱实体和 Monaco 行号；
- 测试失败能跳转到相关代码和知识点；
- 修复后支持“按此结果复测”；
- 结果成为 `project_pipeline` 产物并可比较。

### 5.3 图谱功能补全

#### 知识图谱

- 节点显示来源、版本、难度、掌握证据和置信度；
- 强弱项变化叠加在历史快照中；
- 支持两个快照比较：新增、移除、掌握度变化、路径变化；
- 节点可跳到生成资源、答题明细和审核证据；
- 搜索、路径查找和过滤状态持久化到当前运行视图。

#### 项目图谱

- 实体详情显示来源文件与行号；
- 风险、测试失败、覆盖知识点作为可切换叠加层；
- 点击实体可跳转 Monaco；
- 支持解析快照比较，显示新增/删除/修改实体；
- 项目级流水线与单文件检查使用不同入口和文案；
- 明确解析语言覆盖范围及降级原因。

### 5.4 暂不扩张的功能

- 在“定义驱动执行”接线完成前，不把隐藏的可编辑工作流工作台作为主卖点；
- 不为了图谱效果增加无业务含义的 3D、粒子或自动旋转；
- 不在比赛前承诺全面多语言 AST 支持；
- 不让 AI 自动修改项目代码，除非另设可审阅的补丁流程。

### 5.5 已确认方向：项目语义图谱

项目图谱的正式目标已从“解析更多代码文件”升级为“Agent 读取项目、理解框架并以证据展示架构”。它分为所有已支持语言都可使用的**结构图谱**，以及命中框架适配器且证据充分才启用的**框架图谱**。第一条完整纵切是 Java + Spring Boot；后续按 TypeScript + NestJS、JavaScript + Express、Rust profile、C/CMake/嵌入式 profile 扩展。详见 [项目语义图谱设计](../superpowers/specs/2026-09-02-project-semantic-graph-design.md)。

该方向不承诺一次理解所有语言和框架：未知语言提供侦察报告；已解析但框架未知的项目提供结构图谱；候选框架证据不足时只显示低置信度候选。任何正式框架关系都必须关联源码、配置、依赖或测试证据；Agent 不自动执行未知项目代码或写回源码。

## 6. 视觉、数据面板与动效

### 6.1 去除“AI 模板感”

产品框架中的 Emoji 统一替换：

- Agent 角色：16–18 px 单色线性图标；
- 状态：状态点 + 文案，不使用 ✅、⏳、❌；
- 指标：数字、单位、阈值线，不使用奖杯/火焰等装饰；
- 空状态：克制的本地图形或纯排版；
- 操作按钮：动词优先，如“生成资源”“查看证据”“重新审核”。

允许保留 Emoji 的位置：用户消息、模型生成内容、明确由用户选择的个性化表达。它们不进入导航、Agent 状态和正式报告。

视觉方向继续使用现有深青与珊瑚作为识别色，但控制使用面积：

- 主界面以中性背景、清晰层级和细分隔为主；
- 强调色只用于主操作、选中态和关键风险；
- 减少大面积渐变、胶囊标签、发光边框和过度圆角；
- 统一 4/8 px 间距网格、图标尺寸、卡片边界和正文行高；
- 数据密集页面使用更窄的等宽数字和对齐基线。

### 6.2 数据面板升级方向

高级感来自可比较、可解释、可下钻，而不是更多图表：

1. **顶部摘要**：当前目标、最近运行、画像更新时间、质量是否过阈值；
2. **能力趋势**：理论/实践/掌握度随运行变化，并显示证据数；
3. **盲区与路径**：盲区到知识图谱节点，路径到资源；
4. **质量卡**：幻觉率、适配率、覆盖率，显示阈值、裁判来源和统计时间；
5. **资源有效性**：只有存在阅读、答题、完成等真实交互时才显示；
6. **项目质量**：风险、测试、修复复测趋势，仅在场景二显示；
7. **报告导出**：生成评委可阅读的 HTML/PDF 或打印视图。

不使用没有真实样本支撑的“超过多少用户”或虚假群体基准。

### 6.3 动效系统

建立共享 motion tokens：

```css
--motion-fast: 120ms;
--motion-base: 180ms;
--motion-slow: 240ms;
--motion-ease: cubic-bezier(.2, .8, .2, 1);
```

实施规则：

- 普通切换只动画 `opacity` 和 `transform`；
- 列表增删使用 `TransitionGroup`，删除时保持空间连续；
- 长任务先出现骨架或阶段占位，避免内容到达时整体跳动；
- 图谱布局和拖拽继续使用帧节流；
- 不动画大面积 `width/height/top/left`；
- 所有非必要位移和缩放遵循 `prefers-reduced-motion`；
- 取消/失败状态要有即时反馈，不让动效掩盖状态变化。

体验验收目标：

- 点击后 100ms 内出现视觉反馈；
- 页面/子页过渡 160–220ms；
- 长任务 500ms 内出现第一条阶段反馈或明确等待状态；
- 普通过渡接近 60fps，无明显布局抖动；
- 减弱动效模式下不出现非必要平移和缩放。

无障碍参考：[WCAG 2.2](https://www.w3.org/TR/WCAG22/)、[Animation from Interactions](https://www.w3.org/WAI/WCAG21/Understanding/animation-from-interactions.html)、[CSS `prefers-reduced-motion` 技术说明](https://www.w3.org/WAI/WCAG21/Techniques/css/C39.html)。

## 7. API、底层框架、存储与安全审查

### 7.1 运行时数据路径：P0 数据安全项

安装包已通过 `KMATCH_LOCAL_DIR` 指向用户可写目录，但 `profile_store.py` 和 `run_store.py` 仍使用资源侧 `DATA_DIR`。这可能导致：

- 安装目录无写权限；
- 升级时用户数据丢失或被覆盖；
- 便携版与开发环境行为不一致；
- 图谱数据、画像和运行历史分散在不同根目录。

应新增统一 `runtime_paths` 深模块：

```text
runtime_paths.profiles_dir
runtime_paths.runs_dir
runtime_paths.artifacts_dir
runtime_paths.cache_dir
runtime_paths.legacy_data_dir
```

迁移策略：

1. 新版本首次启动检查旧 `DATA_DIR/profile_archive` 与 `DATA_DIR/workflow_runs`；
2. 使用带版本号的迁移标记；
3. 先复制、校验数量与 hash，再切换读取位置；
4. 迁移失败继续只读旧数据并提示，不能静默丢弃；
5. 用户确认后再清理旧副本；
6. 打包冒烟测试验证升级前后运行和画像仍可见。

### 7.2 API 契约

当前若干接口返回任意 dict，前端通过字段猜测适配。建议：

- 请求/响应使用命名的 Pydantic 模型；
- `/runs`、`/profiles`、`/artifacts`、Agent 事件各自有版本化 schema；
- 统一错误信封：

```json
{
  "code": "MODEL_NOT_FOUND",
  "message": "当前模型不可用",
  "retryable": false,
  "stage": "content_generation",
  "trace_id": "trace_01",
  "details": {"configured_model": "..."}
}
```

- 每次运行、每个 HTTP 请求和 SSE 事件共享 `trace_id/run_id`；
- OpenAPI 生成契约快照，前后端测试使用真实 schema，不手写比真实接口更丰富的 mock；
- 幂等操作支持 `idempotency_key`；
- 删除、重跑、续跑明确返回影响对象和新旧运行关系。

### 7.3 超时、取消与重试

当前前端 API 有较大的全局超时，部分业务又有专用超时。应按操作类型集中定义：

| 操作 | 建议策略 |
|---|---|
| 健康检查/配置校验 | 5–15 秒，快速失败 |
| 普通 CRUD | 15–30 秒，不自动重试写操作 |
| 判分/反馈 | 独立短超时，按现有快失败策略 |
| Agent 工作流 | SSE 心跳 + 阶段超时 + 用户取消 |
| 图谱解析 | 后台任务 + 可取消 + 进度事件 |
| 模型调用 | 仅对可幂等请求做有限指数退避 |

Electron HTTP 代理已具备流取消能力，而 ADR-0007 仍保留“未实现真取消”的旧描述。实现稳定后应更新 ADR，使文档和现实重新一致。

### 7.4 前端依赖与 XSS

本次本地审查结果：

- 根 Electron 包 `npm audit --omit=dev` 未报告生产依赖漏洞；
- 前端依赖链报告 15 项，其中包含 2 项 high、12 项 moderate、1 项 low；

- PostCSS、nanoid 等多为构建链风险，但仍需要锁文件治理。

### 7.5 Electron、Vite 与后端依赖

当前 Electron 33 已结束官方支持。到 2026-09，Electron 官方活跃分支已显著高于 33。参考：[Electron 发布时间表](https://releases.electronjs.org/schedule)、[Electron 发布列表](https://releases.electronjs.org/)、[Electron 43 发布说明](https://www.electronjs.org/blog/electron-43-0)。

升级策略：

1. 比赛前不做主版本升级；
2. 赛后在独立分支先升级 Electron 33 -> 43，执行窗口、preload、sandbox、IPC、sidecar、打包和安装回归；
3. Electron 稳定后，再单独升级 Vite 5 -> 7；
4. 不把 Electron、Vite、Vue 和 UI 框架同时升级；
5. Vue 3.5 当前无需为“追新”而动。

后端 `requirements.txt` 以 `>=` 为主，构建可复现性不足。建议维护：

- 人工维护的 `requirements.in`；
- 从验证环境生成的精确 `requirements.lock`；
- PyInstaller 构建使用 lock；
- 依赖许可证和 CVE 报告；
- Python 运行时版本、模型 SDK 和测试依赖分组。

### 7.6 大模块与架构深化

优先形成以下深模块，而不是新增更多全局 store：

1. **Workflow Run**：工作流定义、事件、状态归约、持久化、续跑、取消；
2. **Learner Profile**：问卷策略、画像 schema、证据合并、版本迁移、Agent 适配；
3. **Artifact History**：产物清单、快照、比较、删除、导出；
4. **Runtime Storage**：所有用户可变数据的目录和迁移；
5. **Operation Policy**：错误、超时、取消、重试、trace id；
6. **Presentation System**：图标、状态、动效、数字和图表格式。

大型视图组件逐步按业务职责拆分，尤其是 `Dashboard.vue` 与 `ProjectGraphView.vue`；拆分标准不是行数本身，而是是否拥有独立状态、规则和测试边界。

### 7.7 健康检查与能力探测

当前 `/api/health` 会调用远程 `models.list()`，而前端又周期性轮询该接口。远程厂商变慢、限流或代理异常时，本地 sidecar 和图存储可能明明正常，却被整体显示为后端异常。建议拆分：

- `liveness`：只判断本地进程存活，不访问网络；
- `readiness`：判断图存储、工作流和本地数据是否就绪；
- `capabilities`：返回 LLM、Embedding、Judge、Search、Sandbox 的缓存能力状态；
- `probe`：仅在用户点击“测试连接”或保存配置时发起远端请求。

sidecar 启动只依赖 liveness；状态栏轮询本地状态；远程能力按缓存和用户操作刷新。这样能避免外部服务拖慢事件循环，也不会把“模型不可达”错误解释为“桌面后端已崩溃”。

### 7.8 桌面后端客户端

浏览器 fetch 与 Electron IPC 是两个真实 transport adapter，但请求、流、SSE、错误、超时和取消仍散落在多个调用方。建议建立 `DesktopBackendClient`：

- 对外只暴露 `request/stream/cancel`；
- 每次请求生成 `request_id`，阻塞 IPC 请求也能通过 AbortSignal 取消；
- transport 层返回 typed error，不直接弹 Element Plus toast；
- UI 层决定错误展示，避免一项故障连续弹两次；
- 数十秒以上的操作返回 run ID，通过事件流观测并可恢复，不长期占用单次 HTTP 请求；
- 明确 Python `asyncio.to_thread + wait_for` 只能停止等待、不能终止底层线程或模型调用，并在执行模型中避免把它误当作真取消。

## 8. 赛题加分功能建议

赛题评分重点是完整性、创新性、体验和实用性。新增功能必须直接增强其中至少一项。

### 8.1 双画像个性化对照（高价值）

用同一目标、两组不同背景画像生成：

- 不同学习路径；
- 不同难度和解释方式；
- 不同实操支架；
- 对比适配率和覆盖率。

这是证明“个性化真实发生”最直观的比赛证据，价值高于继续增加普通设置项。

### 8.2 评审证据包导出（高价值）

一次运行导出：

- 输入画像（脱敏）；
- AgentEvent v2；
- 画像版本 diff；
- 图谱快照；
- 生成资源；
- Reviewer/Judge 报告；
- M5 指标；
- 软件版本、模型配置摘要和内容 hash。

支持 JSON + 可阅读 HTML，必要时打印为 PDF。这样评委可以离开现场界面后复核结果。

### 8.3 隐私与自动决策说明（中高价值）

画像页新增“为什么收集、如何使用、来自哪里、如何删除”。对画像推断和自动路径推荐给出解释与修改入口。中国《个人信息保护法》第二十四条对自动化决策的透明、公平以及拒绝仅由自动化决策作出重大影响的决定提出要求，可作为设计底线参考：[工业和信息化部转载的《个人信息保护法》全文](https://www.miit.gov.cn/jgsj/zfs/fl/art/2022/art_515a4b20c12f430eab54bb4f56d89f56.html)。

### 8.4 降级可见性（中价值）

展示：

- 当前使用嵌入式图还是 Neo4j；
- 语义向量是否就绪，是否降级纯图；
- 联网搜索是否不可用；
- Docker 沙箱是否降级子进程；
- 独立裁判是否同源模型；
- 哪些结果受降级影响。

真实、明确的降级说明比假装所有能力都在线更能建立专业可信度。

### 8.5 暂不建议增加

- 社区、排行榜、好友、教师后台等横向产品系统；
- 大而全课程商城；
- 为展示而做的虚拟数字人；
- 无真实数据支撑的预测分数；
- 全自动改代码并提交；
- 比赛前引入新的云数据库或复杂身份体系。

## 11. 测试与验收矩阵

### 11.1 画像

- 非编程领域从不出现 Python/编程经验；
- Python、JavaEE、数据库、机器学习按规则显示不同字段；
- 未填写偏好时显示“尚未学习”，不伪装成 `read_write`；

- 画像导出和删除符合 UI 说明；
- 旧的 10 组质量夹具仍能运行 M5 回归。

### 11.2 Agent 与运行

- 同一 Reviewer 的两个阶段拥有独立状态；
- 交互模式不会把未触发审核显示成卡死；
- 资源生成后内容审核最终能到 `completed/degraded/failed` 之一；
- SSE 重连不会重复事件，乱序时按 `seq` 归约；

- `/runs` 真实响应与前端 fixture 完全一致；
- 续跑建立父子关系，原运行仍可复盘。

### 11.3 历史与存储

- 从旧 `DATA_DIR` 迁移到 `LOCAL_DIR` 后数据数量和 hash 一致；
- 迁移中断可恢复；
- 删除资源不删除画像；
- 删除运行不会误删其他运行共享的产物；
- 删除项目图谱不会删除源码；
- 本地历史迁移后仍能回看；
- 安装包升级后画像、运行和图谱历史仍存在。

### 11.4 安全与体验

- 恶意节点名、项目名、资源标题不能在 ECharts tooltip 执行 HTML/脚本；
- Markdown/HTML 预览覆盖常见 XSS payload；
- 错误响应不泄露 API key、完整 prompt 或本地绝对敏感路径；
- `prefers-reduced-motion` 下关闭非必要动效；
- 主流程键盘可达、焦点可见、颜色不是唯一状态信号；
- 图谱和列表切换没有明显布局跳动。

### 11.5 比赛演示验收

- 10 分钟内完成场景一闭环并展示三类资源；
- Reviewer 和独立 Judge 的证据差异清晰；

- 断网或某服务不可用时，降级状态可见且核心演示可继续；
- 能导出一份评审证据包。

## 12. 风险、依赖与决策点

### 12.1 主要风险

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 赛前大规模 schema 迁移 | 破坏现有质量回归和提示词 | P0 只做条件显示和兼容字段；v4 放 P1 |
| AgentEvent v2 一次替换 | SSE、续跑、历史同时回归 | 双读兼容，先生成 v2、保留 v1 适配 |
| 历史统一导致数据误删 | 用户不可恢复 | manifest 引用计数、回收站/确认、迁移备份 |
| Electron/Vite 同时升级 | 打包和 preload 风险 | 分支、分版本、分别回归 |
| 数据面板展示虚假精度 | 影响可信度 | 所有指标显示来源、样本和置信度 |
| “透明思考”展示原始模型自述 | 泄密且不等于事实 | 只展示结构化事件、证据和结论 |

### 12.2 建议默认决策

为减少等待，实施时可采用以下默认值：

- 学习偏好问卷默认可跳过；
- 内容资源在诊断完成后自动后台生成并审核，用户可在设置中改为手动；
- 历史默认本地保存，用户可单项删除；
- 删除运行不回滚已聚合画像，但必须明确提示；
- 设置中的学习画像使用独立子页，不放进一级侧栏；
- 比赛前只更名“检查当前文件”，赛后再扩展项目范围；
- 赛前不升级 Electron/Vite 主版本。

### 12.3 需要产品所有者最终确认的问题

这些问题不会阻碍 P0 审查，但会影响 P1 交互：

1. 诊断完成后，资源生成与审核是默认自动开始，还是必须由用户点击？本方案建议自动后台开始。
2. 删除一次运行时，是否提供“同时回滚本次画像影响”的高级选项？本方案建议第一版不提供，避免破坏跨次合并一致性。
3. 内容呈现偏好是否规划音频资源？若没有，就不应询问“听觉偏好”。
4. 项目流水线第一版的最大范围是“变更文件”还是“整个项目”？本方案建议优先变更文件。

## 13. 完成定义

本轮升级完成时，产品应达到以下状态：

- 用户学习任何领域都不会被强制回答无关的 Python 问题；
- 画像清楚区分自填、测评、项目和行为证据，并可按领域查看；
- 每个 Agent 阶段状态与真实工作流一致，内容审核不会永久“待触发”；
- 评委能看到可验证的 Agent 输入摘要、证据、结论、复审和质量指标；
- 运行历史能按场景、领域和项目快速定位，并关联所有产物；
- 图谱和资源可以回看、比较和单项删除，删除后果明确；
- “当前文件检查”和“项目质量流水线”的范围不再混淆；
- 产品框架中不再依赖 Emoji 传达正式状态；
- Dashboard 指标可比较、可解释、可下钻；
- 画像和运行历史统一落在安装包用户数据目录；
- API、依赖、动效和无障碍有可重复的验收基线；
- 所有新增能力都能直接服务赛题完整性、创新性、体验或实用性评分。
